从标题混乱到可检索记忆

这个项目的核心不是“改几个名字”，而是给 Codex 对话建立一套可靠的标题治理系统。

左侧对话标题本质上是你的工作记忆索引。默认标题如果直接截取首句或 goal，就会又长又乱；真正需要的是： 谁的项目、做了什么、最后处于什么状态，一眼能看懂。

13 明显超长标题，是自动治理优先目标。
5min 闲置 5 分钟生成候选，不等于立刻改所有标题。

Problem

问题本质：标题是索引，不是聊天摘要

表象 左侧标题太长、太散、不可找

很多标题直接使用用户首句、完整 goal 或临时口语，过一段时间后无法判断里面到底做了什么。

根因 默认命名没有“检索目标”

它可能能表达开头，却不能表达任务对象、动作、结果和状态，所以标题对未来的你没有帮助。

解法 把命名变成治理流程

先识别内容，再生成候选，再通过质量门，最后用官方接口写入并验证 UI 是否一致。

好标题 = 可识别对象 + 关键动作 + 必要状态。短不是目标，可检索才是目标。
First Principles

第一性原理：为什么要这样设计

原则 1 标题是未来检索入口

标题的第一职责不是好看，而是让你半年后能按“项目、动作、状态”找回这次工作。

原则 2 用户手动权大于自动权

你自己改过的标题代表明确意图，自动 agent 不能覆盖，除非你显式 force。

原则 3 官方协议优先于内部文件

Codex 内部 SQLite 不是稳定 API。能用 thread/name/set，就不直接写库。

原则 4 候选和应用必须分开

5 分钟可以生成候选，但只有坏标题能快速自动应用，普通标题要等任务更稳定。

Architecture

系统方法：三层能力，而不是一个黑盒脚本

手动权限层

提供 `rename-codex "新标题"` 和 `rename-codex thread_id "新标题"`，先满足你随时改名的需求。

历史整理层

对历史 56 个未归档线程生成预览表，人工确认后批量应用，避免一次性误改。

增量 Agent 层

每 5 分钟扫描，坏标题自动治理，普通标题保守更新，长期保持左侧列表清晰。

Fallback 层

只有官方接口不可用且你显式允许时，才考虑 SQLite fallback，并且必须备份和可回滚。

Flow

运行流程：从对话内容到可检索标题

01 读取线程

通过 app-server 获取 thread list 和 thread read，拿到标题、目录、用户目标和结果线索。

02 提取特征

找项目名、对象名、动作词、阻塞点、完成状态，过滤寒暄和长段 goal。

03 生成候选

优先用本地规则，低置信度或长会话再调用 Codex 生成候选。

04 质量门

检查是否可检索、是否过泛、是否覆盖手动标题、是否该自动写入。

05 写入验证

调用 thread/name/set，回读确认；UI 不刷新则重启验证，失败即停止自动化。

Quality Gate

标题质量门：不只是短，而是能找回来

必须具备
✓

包含项目、对象或领域，例如 ProofRoute、GitHub CLI、Codex 历史。

✓

包含动作，例如安装、配置、审计、实现、上传、总结、排查。

✓

必要时体现状态，例如阻塞、待认证、已完成、方案设计。

✓

控制长度，适合左侧栏扫读，不用完整句子。

必须避免
!

避免 `/goal` 原文、首条用户消息、长段提示词。

!

避免“优化项目”“解决问题”“整理内容”这种泛标题。

!

避免覆盖用户手动命名或 `[keep]` 标题。

!

避免在任务还没稳定时给普通标题过早定名。

Roadmap

落地阶段：先可控，再自动

Phase 1 给你手动改名权

先做 `rename-codex`，确保你能随时把当前对话改成自己想要的标题。

Phase 2 历史批量预览

对旧会话生成预览表，你确认后再应用，避免误伤重要标题。

Phase 3 增量自动治理

后台每 5 分钟生成候选，只对明显坏标题自动写入，普通标题保守处理。

最终目标：让 Codex 左侧栏变成“项目工作索引”，而不是一串随机聊天开头。
