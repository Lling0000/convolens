第一性原理版计划

让 AI 对话历史真正可找回

这个项目不是给某一个工具打补丁，而是做一个统一的对话治理层：把 Codex、Claude Code、Cursor、Trae、Qoder、CodeBuddy、Antigravity 等 AI 编程工具里的会话，统一读出来、命名、筛选、索引，并在安全时写回标题。

一句话判断

真正的问题不是“标题不好听”，而是 AI 工具越来越多，历史会话没有统一的可检索语义层。

本地优先 多平台适配 标题治理 外部索引 安全写回

一、从本质看，这个项目解决什么

AI 编程工具正在变成新的工作记忆。你不是只在里面聊天，而是在里面安装软件、配置 GitHub、排查权限、写代码、做产品判断、沉淀长期计划。问题是，这些记忆分散在不同工具里，而且默认标题通常只截取第一句话。

所以核心问题不是“重命名”，而是“把分散的 AI 工作记忆变成可检索、可治理、可迁移的知识索引”。

1

对话是工作资产

每个会话都包含目标、过程、结果、阻塞和决策，不应该只按时间堆在侧边栏。

2

标题是检索入口

好标题必须说明对象和动作，例如“GitHub CLI：浏览器认证阻塞”。

3

平台不能被强改

能用官方接口就用官方接口；不能写回就做外部索引，不破坏原工具。

二、最小抽象是什么

所有工具都可以先被抽象成同一种东西：一个 provider 下面有很多 conversation，每个 conversation 里有 turns、workspace、title、status 和 artifacts。

发现

找到各平台的会话来源：API、JSONL、SQLite、导出文件或 CLI。

解析

提取用户目标、关键动作、结果、阻塞、项目路径。

命名

生成“对象：动作状态”的可检索标题。

索引

统一写入本地搜索库，支持跨工具筛选。

写回

只有官方或验证安全的平台才写回原工具。

三、平台适配不能一刀切

不同 AI 工具的开放程度不同，所以必须分层适配。这个设计比“直接改每个工具的数据库”更稳。

层级 能力 含义 适用情况
L0 只读导入 只读取历史，不改原工具。 Claude Code JSONL、未知平台导出文件。
L1 外部索引 生成标题和摘要，但只存在 ConvoLens 自己的索引里。 没有稳定写回 API 的工具。
L2 官方写回 通过官方协议、CLI 或 API 改标题。 Codex app-server 的 thread/name/set。
L3 验证后本地写回 确认 schema、备份、回滚后，才允许改本地库。 Cursor 这类本地 SQLite 场景。

四、第一版怎么做

阶段 1：先能统一看见

做扫描器和本地索引。先支持 Codex、Claude Code、Cursor 的只读导入，解决“历史分散”的问题。

阶段 2：再能安全命名

生成标题预览，支持手动确认和批量应用。Codex 走官方写回，其他平台先走外部索引。

阶段 3：最后做自动治理

后台每 5 分钟扫描，但只自动修复明显坏标题；普通标题进入预览，不贸然覆盖。

最重要的产品判断

“全部适配”不等于“全部强行写回”。真正稳定的开源项目应该先统一读和搜，再按平台能力逐步解锁写回。这样既能覆盖 Codex、Claude Code、Cursor、Trae、Qoder、CodeBuddy、Antigravity，也不会因为某个平台升级内部存储就把用户历史弄乱。

五、标题标准

标题要像一个索引项，而不是一句聊天开头。标准格式是：

对象 / 项目 / 平台：动作 + 状态

差标题 好标题 为什么好
帮我配置一下 GitHub CLI：浏览器认证配置 有对象，有动作，能搜索。
/goal 做一个高 star 项目... ProofRoute：构建 LLM 路由器 保留项目核心，不保留长提示词。
继续 Codex 历史：自动重命名方案 说明这轮到底在推进什么。

六、最终形态

ConvoLens 最终应该像一个 AI 工作记忆总控台：你可以搜“GitHub 权限”“老板预审”“LLM 路由器”“Token 统计”，它会跨 Codex、Claude Code、Cursor、Trae、Qoder、CodeBuddy、Antigravity 找到相关会话，并告诉你当时做了什么、结果是什么、哪里阻塞。

这才是第一性原理下的核心：不是美化侧边栏，而是把 AI 编程过程中的分散记忆重新组织成可复用资产。
